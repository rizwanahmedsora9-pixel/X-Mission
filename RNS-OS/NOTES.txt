RNS-OS release notes
====================

RNS-OS 1.0.1 — "there is no ISO in the repository"
=================================================

Reported: "how to run RNS OS in VirtualBox, I can see no ISO image; compile
the ISO and give the settings and install steps."

There was no ISO anywhere, and no way to make one:

  A. dist/ and *.iso are gitignored on purpose — the Debian base image alone
     is ~660 MB. The ISO is built, never committed.
  B. The one URL build-iso.sh knew about was dead. Debian keeps only the
     CURRENT stable in /debian-cd/current/ and moves every older point release
     to /cdimage/archive/; Debian 13 is current now, so
     .../current/amd64/iso-cd/debian-12.11.0-amd64-netinst.iso is a 404.
     ./build-iso.sh therefore could not download a base image at all, on any
     machine, and no ISO had ever been produced.

What changed
------------
1. iso/build-iso.sh — base image candidates are the two Debian 12 ARCHIVE
   images (12.15.0, then 12.11.0), each pinned to the sha256 Debian publishes
   in the SHA256SUMS beside it. A candidate that 404s, downloads as HTML or
   fails its hash is skipped for the next one; an unknown --url falls back to
   fetching that SHA256SUMS. The base image is now validated BEFORE the
   xorriso check, so a 404 saved as .iso reports itself instead of hiding
   behind a missing tool. --base uses a local copy, --check validates without
   burning.

2. .github/workflows/build-iso.yml (new) — builds the ISO on a GitHub runner:
   appliance test suite, verified download, burn, then it proves the preseed
   and payload are inside the image, writes SHA256SUMS, uploads the ISO as an
   artifact, and attaches it to a Release when a rns-os-* tag is pushed. This
   is the only route for an operator without a Linux box, WSL or Docker.
   (GitHub Actions has to be enabled for the repository: Settings > Actions.)

3. defaults.env — RNS_MODE=wired and GUEST_IF=enp0s8. The old default was
   `wifi`, which in a VM with no passed-through dongle left the customer side
   dead on first boot: portal up, no customer could ever get a lease. `wired`
   works with no extra hardware, because Adapter 2 is the customer port.

4. defaults.env — ADMIN_LAN=1. The engine writes ADMIN_LAN=0 into its own
   config.env template, and 0 means "/admin answers only from this box". The
   operator's browser is never on the box: through VirtualBox NAT the request
   arrives from an address that is not the box, so the panel answered "Staff
   only — open this page on the shop phone" to the very person who installed
   it. firstboot now applies the RNS-OS value over the engine's (on a genuine
   first boot only, so a later operator choice wins), and the panel is still
   behind the staff password.

5. rns-os-ctl — firstboot no longer depends on the NIC being called enp0s8:
   guest_if_detect() takes the spare wired adapter when the configured one is
   not present, never the uplink (it owns the default route) and virtual
   interfaces only as a last resort. New `rns os mode wired|wifi|off` switches
   the customer side and restarts the units, instead of editing two keys and
   restarting four units by hand.

6. create-vm.sh / create-vm.ps1 — NAT port forwarding bound to 127.0.0.1
   (panel 8080 -> 8080, SSH 2222 -> 22, host port auto-shifted when busy), the
   host-only adapter is put on the appliance's own 192.168.50.x subnet instead
   of VirtualBox's default 192.168.56.x (which left the host unable to reach
   192.168.50.1 at all), and the ISO is checked for the ISO9660 magic before a
   VM is built, so pointing --iso at the wrong file fails immediately instead
   of at "FATAL: No bootable medium".

7. iso/vm/VirtualBox.md — rewritten as the complete walkthrough: how to get an
   ISO (CI, Linux/WSL, Docker), every GUI setting, both CLI paths, the
   unattended install, first login, reaching the panel from the PC, the
   customer-side test, Wi-Fi dongle passthrough, troubleshooting table.

Tests
-----
tools/os-selftest.sh: 127 -> 163 checks, ALL PASSED. New coverage:
  - customer-interface detection, driven through a synthetic /sys tree and a
    fake `ip` (a VM-like tree with enp0s3/enp0s8, and a tree with nothing
    spare), so it is tested on any build host regardless of its real NICs
  - `rns os mode wired|wifi|off`, including the unknown-mode rejection
  - the shipped defaults (mode, interface, ADMIN_LAN) as a contract
  - build-iso.sh: a 404 page saved as .iso is refused, a sha256 mismatch is
    refused, both without network or xorriso
  - create-vm.sh/.ps1: the forwards, the 127.0.0.1 binding, the host-only
    subnet and the pre-flight ISO check
  - the CI workflow exists, runs the suite, uploads an artifact and publishes
    for a rns-os-* tag

Still open / not verified here
------------------------------
- No ISO is attached to the release of this work: GitHub Actions is disabled
  on this repository, so the workflow has not run yet. Enable it (Settings >
  Actions > General), then push the tag `rns-os-1.0.1` or run the workflow by
  hand. Until then the local route is `cd RNS-OS/iso && ./build-iso.sh` on
  Linux/WSL/Docker.
- create-vm.sh and create-vm.ps1 are syntax-checked and their settings asserted
  by the test suite, but neither has been run against a real VBoxManage (not
  installed in the build environment). Run one once and report what it says.
- The installer itself has still never been booted in a VM from this tree.
  preseed placement, menu patching and the payload staging are exercised by the
  test suite against the real code; the 5-10 minute install is not.


RNS-OS 1.0.0 — the gateway as a VirtualBox appliance
====================================================

(1.0.0 was never built or released as an ISO: see 1.0.1 above for why,
and for what had to change before an ISO could exist at all.)

This is the FIRST release of a separate product line. It is not v8 of the
Magisk module and it does not touch releases/v3 … v7. Magisk releases keep
their own count; RNS-OS keeps its own (1.0.0, then 1.1.0, …).

What it is
----------
The RNS Gateway — captive portal, voucher codes, package builder, sales
report, JazzCash/EasyPaisa auto-payment, staff panel — built as a bootable
Debian 12 ISO that installs itself into an Oracle VirtualBox VM.

It runs the SAME engine files as the Magisk module (copied in at build time
from ../RNS-Gateway/module/rns, verified byte-identical by the test suite),
on a Linux platform layer instead of Android: systemd units, hostapd,
dnsmasq, ip/tc.

Build and run
-------------
  cd iso && ./build-iso.sh
  ./vm/create-vm.sh --iso ../dist/RNS-OS-1.0.0-amd64.iso --start

Windows host:  iso\vm\create-vm.ps1 -Iso ..\dist\RNS-OS-1.0.0-amd64.iso -Start

The installer is unattended. Log in as root / rnsos, run `passwd`, then
`rns os setup`.

Test checklist for RNS-OS 1.0.0
-------------------------------
On the build machine (no VM needed, no root, no internet):
  □ tools/os-selftest.sh                     -> "ALL PASSED (127 checks)"

In the VM, after the installer reboots:
  □ rns os status shows guest interface, portal URL, pages + supervisor running
  □ the login banner prints the staff panel URL and the generated password
  □ open the staff panel from the host browser, log in
  □ Settings > Package builder -> build a package -> Sell -> generate a code
  □ from a client on the customer side: the captive portal appears, the code
    works, browsing starts
  □ Sales tab shows the code under Today with the right rupee total
  □ Settings > Payment gateway -> set a JazzCash number
  □ Settings > Online packages -> build one online package
  □ client: Buy Online -> pick it -> enter a TID -> internet starts and the
    PDF receipt downloads
  □ Payments tab shows the payment as confirmed with its voucher code
  □ rns os diag produces one bundle you can paste into a report

What was checked in v7 while building this
------------------------------------------
1. releases/v7/RNS_Gateway.zip is byte-identical to RNS-Gateway/RNS_Gateway.zip
   (md5 ea3c132e4c14bd415e59e10c3d1f1209) and its 25 files match the source
   tree. The x86_64 listener is absent from the zip on purpose — build.sh
   excludes it ("Phone zip should include arm binaries, not the lab x86
   binary"), it is not a packaging mistake.

2. v7's own test suite passed: tools/selftest.sh -> ALL PASSED (102 checks),
   and tools/isolate-check.sh -> isolation checks passed.

3. BUT the payment gateway — the whole point of v7 — had ZERO test coverage.
   `grep -c pay tools/selftest.sh` returns 0. v6's features have about 35
   checks; v7 added nine API endpoints, TID validation, auto-verify and a PDF
   receipt with none. Two real defects were sitting in that gap:

   A. NO PAYMENT COULD EVER BE ACTIVATED. The payment record was written with
      17 columns instead of the documented 16 — one separator too many between
      `created` and `seconds`:

          printf '%s|...|%s||||%s||%s|%s\n'   (v7: four pipes)

      so the duration landed in slot 14 and slot 13 was empty.
      online_payment_confirm reads slot 13, saw nothing, and returned
      bad_package. Every customer who paid saw "Payment verification failed.
      Please try again or contact the counter." — and manual confirm from the
      Payments tab failed the same way. v7's headline feature could not work
      at all.

      Fixed in RNS-Gateway/module/rns/bin/store.sh (both write sites), plus
      payments_schema_migrate() which repairs 17-column rows already written,
      keeps a rollback backup (payments.tsv.pre-16col.bak) and runs once
      (marker .pay16) — the same pattern v6 used for the voucher schema.

   B. AUTO-VERIFY ACCEPTED ANY WALLET NAME. online_payment_create checks the
      method against jazzcash|easypaisa; online_payment_auto_verify did not.
      validate_tid only applies a digit rule inside its jazzcash and easypaisa
      branches, so an unknown method skipped format validation entirely and a
      6-character TID such as "ABCDEF" was accepted as a paid payment.
      Fixed: auto-verify now rejects an unknown wallet up front (bad_method).

   Both fixes are in the shared engine, so the phone and the appliance get
   them from one place. tools/os-selftest.sh now covers the whole payment
   flow (38 checks) so this cannot regress unnoticed.

4. RNS-Gateway/RNS_Gateway.zip was rebuilt with tools/build.sh so the zip
   matches the fixed source (store.sh 53093 -> 55452 bytes, same 25 files).
   releases/v7/RNS_Gateway.zip is left exactly as released.

5. STILL OPEN, your call, not changed here:
   - module.prop in the v7 zip still says version=6.0 / versionCode=60 with
     the v6 description, identical to the v6 zip. After flashing v7, Magisk
     shows "RNS Gateway 6.0", so there is no way to confirm v7 is the build
     running — every earlier release's checklist relied on that string.
     Bumping it to 7.0 is a one-line change but it is a release decision.
   - releases/v7/RNS_Gateway.zip is named without the _v7 suffix that
     releases/v3 … v6 use.
   - releases/v7/NOTES.txt says "Rate limit: max 5 payment attempts per
     device per 10 minutes". The manual path limits 3 pending per IP; the
     auto-verify path counts 5 records per IP. Both are now tested; the
     sentence in the notes is the thing that is imprecise.
   - tools/selftest.sh (the Magisk suite) still has no payment coverage.
     RNS-OS/tools/os-selftest.sh covers it against the same engine files.

What was NOT verified here
--------------------------
The build machine for this release had no network access and no root, so:
  - no ISO was burned (xorriso absent, Debian netinst not downloadable).
    build-iso.sh is verified up to that point: the payload staging, the
    preseed placement and the boot-menu patching are all exercised by
    os-selftest.sh, including the real `build-iso.sh --patch-menu`.
  - no VM was booted. VBoxManage is absent, so create-vm.sh and
    create-vm.ps1 are syntax/structure checked only.
  - hostapd, dnsmasq and iptables are absent here, so the radio and the
    firewall gate were not run. The gate itself is the engine's net.sh, which
    the Magisk suite already tests against a fake iptables.
Everything above is stated in RNS-OS/README.md too. Run the ISO build and the
VM once on a machine with network and report back what you see.
